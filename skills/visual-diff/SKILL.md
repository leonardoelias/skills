# visual-diff

Renders the app's affected routes at the PR's **base** and **head**, compares the screenshots and
publishes a comment with `Before | After | Diff` images and a UX summary. The mechanics are
scripted; your job is the judgment: which routes matter, what the changes mean for the people who
use the app, and whether everything is fine to publish.

`$SKILL` is the folder that contains this file. Run the CLI like this:

```bash
node "$SKILL/bin/visual-diff.mjs" <command> [options]
```

The first use installs the dependencies; the first capture downloads Playwright's Chromium (~150 MB).
Every command prints JSON on stdout and progress on stderr. Output goes to `.visual-diff/` at the
repository root, which is added to `.git/info/exclude` automatically.

## Privacy rules (always)

- Screenshots never go to public or third-party hosts (imgur, gists, Slack, CDNs). The only
  destination is the `visual-diff-assets` branch of the repository itself.
- `publish` refuses public and `INTERNAL` repositories (visible to the whole company) unless the
  user explicitly asks for `--allow-public-repo` / `--allow-internal-repo`. If the visibility is
  public, internal or unknown, stop and ask.
- Before publishing, look at the images for personal data, e-mails, tokens or production data on
  screen. If you find any, don't publish: mask it (`capture.mask`) and run again.
- Credentials come only from environment variables (`"$NAME"` in `auth.headers`/`auth.cookies`) or
  from a file generated by `login`. Never print secret values or put them in the summary or the comment.

## 1. Context

```bash
gh pr view <n> --json number,url,baseRefName,headRefName,headRefOid   # or: gh pr view (current branch)
git status --short
```

- Look for `visual-diff.config.json` at the repo root. If it doesn't exist, run `init` (in monorepos
  it picks the `appDir`), check `startCommand`, `appDir` and `routes`, and offer to commit the file.
  `doctor` checks git, gh, Chromium, config and visibility: FAIL blocks; WARN (no gh, no remote)
  only matters for `--pr` and `publish`. `doctor --smoke` starts the current app and captures one
  route: use it when the `startCommand` is new.
- **Publishing to a PR:** pass `--pr <n>` so the head is the pushed commit. Warn about uncommitted
  or unpushed work, because it won't show up.
- **Looking at work in progress:** omit `--head`; the working tree (with uncommitted changes) is
  copied into a worktree and labeled as such (that report can't be published).
- **Deployed previews:** `--base-url` and `--head-url` together (see `references/privacy.md`).
- **Pages behind login:** `login --url <login page>` opens a browser for the user to sign in and
  saves the session; then `auth.storageState` + `auth.origins: ["local"]` in the config.

## 2. Detect changed UI and pick routes

```bash
node "$SKILL/bin/visual-diff.mjs" detect --pr <n>
```

Maps changed files to routes through the config's `routes[].files` and `globalFiles`, then by
framework convention (Next.js app/ and pages/, SvelteKit, Astro, Nuxt, Remix, static HTML;
layouts cover the routes below them, the root layout and `_app` cover all of them) and by an import
graph that resolves tsconfig aliases, `#imports` and workspace packages. The JSON lists each route
with `reasons`, `confidence` and `change` (`added`, `removed`, `modified`), plus:

- `unmatched`: UI files with no route. Find the pages yourself and pass them with `--routes`.
- `unmatchedMaybe`: `.js`/`.ts` outside interface folders with no route; may be backend only.
- `needsExample`: dynamic routes (`/blog/[slug]`). Find a real id and pass `--routes /blog/hello`
  (or put the example in `routes` in the config, and it gets used on its own from then on).
- `notes` and `droppedRoutes`: routes cut by `detect.maxRoutes`, `appDir` hint in monorepos.

If no UI file changed, say so and stop; don't generate an empty report. Tell the user in one or
two lines which routes you'll capture and why. Keep track of the affected routes that won't be
captured (login, modals, limits): they go in the summary, so "no change" isn't read as "all good".

## 3. Capture and compare

`run` starts two servers and takes dozens of captures: **run it with a 10-minute timeout**
(`timeout: 600000` in the Bash tool) **or in the background**, following stderr. The first
stderr line gives an estimate. If the process gets killed, the next `run` cleans up leftover
servers and worktrees (or run `cleanup`).

```bash
node "$SKILL/bin/visual-diff.mjs" run --pr <n> [--routes "/,/pricing"] [--viewports desktop,mobile] [--themes light,dark]
```

In one go: creates worktrees for base (the merge-base) and head, prepares dependencies (links
`node_modules` or installs when the lockfile changed), starts both sides at the same time on free
ports, captures route × viewport × theme alternating base and head, compares with vertical
alignment (content that only moved down doesn't count as changed, but the shift is reported),
builds the images (full page and crops of the changed regions) and cleans everything up. Captures
are deterministic: animations zeroed, fonts and images awaited, `Math.random` and `crypto` seeded,
clock frozen, videos paused, iframes masked, analytics and chats blocked, and each screenshot is
retaken until two captures in a row are identical.

stdout carries a summary (`stats`, `changed`, `added`, `removed`, `failed`, `warnings`,
`notCaptured`); the detail is in `.visual-diff/report.json` (`--json full` prints everything). Each
item has a `kind`: `content` (pixels changed), `layout-shift` (spacing only: see `shifts`),
`added` (new page) or `removed`. Use `--themes light,dark` when colors or tokens changed.

- Tune without recapturing: change `diff.*` in the config and run `diff`.
- Recapture one route or key: `run … --only /pricing` (or `--only home__mobile__light`).
- If it fails, the error names the step (`step`) and the log is in `.visual-diff/logs/`; see
  `references/troubleshooting.md`, fix the cause and run again. A failed `run` doesn't delete the
  previous report. Never publish a result from only one side.

## 4. Review and write the UX summary

Open the images before writing (first the `compare/*__focus-*.png` crops, then the full
compositions). Read `.visual-diff/report.json` for the numbers and start from
`.visual-diff/summary.auto.md`. Write `.visual-diff/summary.md` for a designer or PM who won't
read the code (`run` moves an old `summary.md` to `summary.prev.md`):

```markdown
**What changed**
- **Primary button**: more padding and rounder corners. The link next to it moves to the right.
- **Newsletter**: the "Work email" label now uses the brand color.

**Worth a look**
- In the dark theme the blue label on the dark background seems to have low contrast.

**Not verified:** `/settings` (needs login).
```

Guidelines: start "worth a look" with what looks unintentional (a page that changed without its
files changing, a break in only one viewport, contrast, values outside the design system, new
accessibility problems). For `layout-shift`, say the content below y moved down N px instead of
calling the sections changed. A "did not stabilize" warning points at something that moves on its
own and suggests a selector: don't describe it as a change, and suggest `capture.mask`. Say
"changed", not "changed on purpose". Keep it proportional: a swapped color is worth one item. If
you can't see images, write from `report.json` and say so.

```bash
node "$SKILL/bin/visual-diff.mjs" render     # preview: .visual-diff/comment.preview.md
```

## 5. Publish a sticky comment

Publishing writes to a shared PR and pushes a branch: show the summary to the user and ask for a
yes first, unless the request already said to publish.

```bash
node "$SKILL/bin/visual-diff.mjs" publish --pr <n> --dry-run   # lists uploads and problems; sends nothing
node "$SKILL/bin/visual-diff.mjs" publish --pr <n> --verify
```

- Read `publishable` and `problems` from the dry run. Items marked `[blocking]` stop the real
  publish: public or internal repo, unknown visibility, report from another commit (the PR got
  commits after the `run`: run again), report from the working tree with local changes, or a
  `summary.md` older than the report. Tell the user; don't add `--allow-*`, `--assume-private` or
  `--force-stale` on your own.
- The images go to the orphan branch `visual-diff-assets` (a single commit, other PRs' files kept)
  and are linked as `https://github.com/<owner>/<repo>/raw/visual-diff-assets/…`, which only
  renders for people who can read the repo. `--verify` checks the files on the branch and that the
  link asks for login.
- The comment is found by a hidden marker and edited in place; someone else's is never edited (a
  new one is created and the result says so).
- No PR yet: use `render` and offer to publish once the PR exists.

| Output | Meaning |
|---|---|
| exit 0, `status: ok` | report generated |
| exit 0, `status: no-ui-changes` | no UI file changed: say so and stop |
| exit 0, `status: no-mapped-routes` | only `.js`/`.ts` that may be backend; decide whether to pass `--routes` |
| exit 2, `status: no-mapped-routes` | UI changed with no route: find the pages and pass `--routes` |
| exit 1 | error (the JSON has `error` and `step`) |
| exit 3 | git couldn't push (permission, fork, rule that blocks force-push): `--no-upload` |
| exit 4 | publish refused (see `problems`) |
| exit 130/143 | interrupted; servers and worktrees were cleaned up |

## 6. Wrap-up

Report the comment link, the counts, the "worth a look" items and what wasn't captured. If you
found routes, masks or dynamic ids, offer to save them in `visual-diff.config.json`.
After PRs close, `node "$SKILL/bin/visual-diff.mjs" prune --closed` removes their images.

All config options: `references/config.md`. Variants, accessibility, motion and tokens:
`references/audits.md`. Hosting, privacy and protected previews: `references/privacy.md`.
Failures and unstable captures: `references/troubleshooting.md`. Testing the publish flow in a
sandbox repo: `references/publish-test.md`.
